## Что такое cJunosEvolved на самом деле

**Это не коммутатор.** Образ эмулирует транспортные маршрутизаторы PTX:

- `CPTX_COSIM: "BX"` → PTX10002-36QDD (ASIC Express 5), 36 интерфейсов
- `CPTX_COSIM: "BT"` → PTX10001-36MR (ASIC Express 4), 12 интерфейсов

Это прямо влияет на план статьи: роль leaf с VXLAN-туннелями и обучением
MAC на PTX под вопросом, роль spine (чистый IP-андерлей плюс рефлектор
маршрутов EVPN) — нет. Проверяется на стенде.

## Механика containerlab

- kind: `juniper_cjunosevolved`
- Учётка по умолчанию: `admin` / `admin@123`
- Загрузка до приглашения — **около 5 минут** на узел (по докам; свой
  замер ниже, когда будет)
- **Имена интерфейсов в топологии — линуксовые, не джуниперовские:**
  `eth0` — менеджмент, `eth1`–`eth3` **зарезервированы, не трогать**,
  `eth4` и дальше = `et-0/0/0` и дальше в CLI.
  То есть в `links` пишем `cevo:eth4`, а в конфиге `et-0/0/0`.
- В пользовательском startup-config обязателен токен `FXP0ADDR`
  на месте адреса менеджмент-интерфейса, иначе управление только
  через прямой CLI.
- Канализированные интерфейсы в containerlab не поддерживаются.
- Готовый пример на этой же машине:
  `/etc/containerlab/lab-examples/srlcjunosevo/`

## Как попасть в CLI

`docker exec <node> cli -c "команда"` **не работает** — отдаёт только
приглашение и молчит. Причина: cJunosEvolved это KVM-ВМ внутри контейнера,
и `cli` в контейнере лишь обёртка над консолью ВМ.

Рабочий способ — SSH на адрес, который выдал containerlab:

```
sshpass -p 'admin@123' ssh -o StrictHostKeyChecking=no admin@172.20.20.2 "show version"
```

Многострочные конфиги заходят обычным heredoc в тот же SSH — CLI читает
stdin построчно, включая `configure private` / `commit check` / `rollback`.

## EVPN-VXLAN на PTX: проверено

Опасение, что cJunosEvolved (PTX, транспортный маршрутизатор) не потянет
роль листа, **не подтвердилось**. На узле прошёл `commit check` для полного
набора листа:

```
set routing-instances MACVRF1 instance-type mac-vrf
set routing-instances MACVRF1 service-type vlan-based
set routing-instances MACVRF1 protocols evpn encapsulation vxlan
set routing-instances MACVRF1 vtep-source-interface lo0.0
set routing-instances MACVRF1 vlans v10 vxlan vni 10010
```

Ответ: `configuration check succeeds`.

Оговорка, которую надо держать в голове: `commit check` проверяет синтаксис
и часть семантики, но не доказывает, что дата-плейн реально инкапсулирует
VXLAN. Доказательство — трафик между двумя узлами, это следующий шаг.

## Фабрика из двух листьев: заработала (10.10.2026)

`topology/evpn-2leaf.clab.yml`, конфиги `configs/leaf1.conf` и `leaf2.conf`.
Два PTX back-to-back, eBGP-андерлей по прямому линку, eBGP-оверлей lo0↔lo0
с `family evpn signaling`, MAC-VRF с VNI 10010, два хоста в VLAN 10.

Результат: **`ping h1 → h2` — 0% потерь, RTT 1.1 мс через VXLAN.**
Дата-плейн PTX действительно инкапсулирует, вопрос «потянет ли PTX роль
листа» закрыт экспериментом, а не доками.

### Главная грабля всей сборки

Фабрика собралась и выглядела идеально: обе BGP-сессии `Establ`, type-2 и
type-3 разошлись в обе стороны, у каждого листа в MAC-таблице MAC чужого
хоста с флагом `DR` через `vtep-54.32770`, VTEP-эндпоинты на месте, lo0
пингуется. **И при этом ни одного пакета между хостами.** ARP висел в
`INCOMPLETE`.

Разбор по захватам:

1. tcpdump на андерлее со стороны отправителя — VXLAN с VNI 10010 уходит.
2. tcpdump на андерлее со стороны получателя — тот же пакет **приходит**.
3. tcpdump на хосте за получателем — **ноль**.

То есть пакет доезжает до egress VTEP и умирает там. Симметрично в обе
стороны. Счётчики ошибок и drops на интерфейсах — нули, в логах ничего.

Причина нашлась одной строкой в списке ограничений cJunosEvolved:

> For cJunosEvolved to function correctly as a VXLAN Tunnel End Point (VTEP),
> you must configure tunnel termination using the `set forwarding-options
> tunnel termination` command. Otherwise, the traffic in the tunnel drops on
> the egress VTEP.

Лечение — одна строка на каждый узел:

```
set forwarding-options tunnel-termination
```

Применяется на живую, перезагрузка не нужна. Сразу после `commit` ARP
резолвится и пинг идёт.

Почему это хороший материал для статьи: отказ **немой**. Нет ни ошибки,
ни лога, ни счётчика — весь контрол-плейн рапортует успех, а трафика нет.
Человек, который верит выводу `show evpn database`, будет искать проблему
в BGP и политике ещё долго.

## Ограничения платформы, важные для замеров

Из того же списка — то, что напрямую бьёт по методике статьи:

- **Максимум 2000 pps** и 3–5 Мбит/с суммарно по всем интерфейсам.
  COSIM «надёжно работает до 2000 pps на длинах 128–1500 байт».
  Значит поток для замера — не выше ~1000 pps, иначе меряем не сеть,
  а потолок симулятора.
- **Явно не поддерживаются «QoS и протоколы с агрессивными (sub-second)
  таймерами, включая BFD».** Это бьёт прямо в задуманную матрицу
  «дефолтные таймеры BGP против BFD 300 мс × 3»: на эмуляторе агрессивный
  BFD может не отработать штатно.
- Нет MC-LAG, нет VRRP, нет IPv6 в андерлее и оверлее (для BT).
  ESI-LAG отдельно проверять.

Вывод для текста: абсолютные миллисекунды с этого стенда **нельзя**
подавать как «столько теряет PTX». Честная подача — механика и порядок
величин: что отказ бывает трёх разных видов, что разница между ними
на порядки, и откуда берётся hold-time в 90 секунд.
